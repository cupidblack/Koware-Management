======================================================================
0. PURPOSE
======================================================================

This document establishes the working architecture for the Classies
Chronicles AI Desk and the episode system that surrounds it.

It incorporates the feasible recommendations from the earlier Studio
Blueprint work, the v20.x/v21.x AI Desk proposals, the GitHub/Copilot
commissioning proposal, and the latest operational requirements.

This document intentionally does NOT refactor the wider Studio Structure
Skeletal Blueprint. It defines the AI Desk and Chronicles episode system
as a commissioning-ready subsystem that can later be incorporated into
the wider Studio Blueprint.

The architecture is based on one central distinction:

    CC_AI_DESK = HOW THE AI THINKS, BEHAVES, SEARCHES AND ASSISTS.

    EPISODE ARCHIVE = WHAT HAPPENED, WHAT WAS RESEARCHED,
                      WHAT WAS PRODUCED AND WHAT WAS APPROVED.

The AI Desk is therefore a persistent franchise-level intelligence layer,
not an episode-specific assistant and not an episode database.

======================================================================
2. CORE ARCHITECTURAL PRINCIPLES
======================================================================

2.1 ONE AI DESK

There is exactly one permanent:

    CC_AI_DESK/

for the Classies Chronicles franchise.

Do NOT create:

    E01/AI_DESK/
    E02/AI_DESK/
    E03/AI_DESK/

The AI Desk persists across seasons and episodes.

2.2 EPISODE OWNERSHIP

Episode-specific information belongs to the episode.

Examples:

- current news headlines
- current research
- Bible reference used by that episode
- Health & Safety reference used by that episode
- continuity references
- storyline notes
- participants
- consent state
- licensing state
- transcript
- show notes
- production requirements
- AI context snapshot
- post-episode analysis

2.3 CONTROLLED RETRIEVAL

The AI Desk does not automatically search everything.

Every query has a retrieval scope.

Initial scopes:

    CURRENT_EPISODE
    CURRENT_SEASON
    ALL_APPROVED_EPISODES
    GLOBAL_CHRONICLES

A producer may explicitly broaden the scope.

The AI must not silently broaden:

    CURRENT_EPISODE -> ALL_EPISODES

2.4 REBUILDABLE INDEX

The catalog and search index are derived data.

The authoritative source remains the filesystem/archive.

If the database is deleted, it must be possible to rebuild it from the
episode archive.

2.5 CONSENT AND LICENSING ARE ACCESS CONTROLS

A source being indexed does not automatically mean that the source can
be used for every purpose.

Retrieval permission and publication permission are separate concepts.

2.6 GOVERNED PERSONA EVOLUTION

The AI may identify possible improvements to its personality or
relationships, but it does not silently rewrite itself.

The lifecycle is:

    OBSERVATION
        ->
    PROPOSAL
        ->
    PRODUCER REVIEW
        ->
    APPROVE / REJECT
        ->
    VERSIONED PERSONA CHANGE

2.7 LEAN-FIRST IMPLEMENTATION

Do not commission vector databases, FAISS, semantic embedding
infrastructure, autonomous agents, complex cloud orchestration or
virtual audio systems until an actual production requirement justifies
them.

2.8 AUTOMATE PREPARATION BEFORE EDITORIAL JUDGEMENT

Future Tuesday/Friday automation should automate research, organization,
validation and preparation before attempting autonomous editorial
decisions.

======================================================================
3. PHYSICAL / SOFTWARE RESPONSIBILITY
======================================================================

The AI Desk is primarily hosted on the HP Pavilion.

The Pavilion is responsible for:

- AI Desk runtime
- retrieval
- producer control surface
- AI provider connections
- TTS when commissioned
- episode preparation automation
- archive scanning/indexing
- persona governance tooling

The ENVY remains the primary production/recording workstation.

The existing physical audio architecture remains the canonical path
until a demonstrated need requires another architecture.

AI audio is treated as a separate controllable source.

AI MUTE must be independent enough that a software failure cannot leave
the producer without a practical way to silence AI audio.

6. WHAT BELONGS IN CC_AI_DESK
======================================================================

The AI Desk may permanently own:

- persona
- intellectual style
- voice rules
- behavioural rules
- safety/boundary rules
- relationship models
- prompt methodology
- prompt versions
- provider configuration
- runtime configuration
- retrieval configuration
- source catalog
- rebuildable search index
- source hashes
- source status
- permission state required for retrieval
- automation definitions
- producer controls
- system logs
- architecture documentation

The AI Desk must NOT become the permanent home of:

- raw video
- raw audio
- full episode media
- episode news archives
- guest contact databases
- arbitrary member exports
- episode-specific research as permanent global knowledge
- unapproved private material
- unpublished personal information

The AI Desk stores references and derived intelligence infrastructure,
not the entire archive.

7. PERSONA ARCHITECTURE
======================================================================

The AI personality is a persistent system.

Minimum files:

    01_PERSONA\
    |
    +-- CC_AI_PERSONA_BASE_v0.1.txt
    +-- CC_AI_PERSONA_INTELLECTUAL_STYLE.txt
    +-- CC_AI_PERSONA_VOICE.txt
    +-- CC_AI_PERSONA_BEHAVIOURS.txt
    +-- CC_AI_PERSONA_BOUNDARIES.txt
    |
    +-- relationships\
    |   +-- CC_AI_PERSONA_RELATIONSHIP_{{username}}.txt
    |
    +-- proposals\
    +-- approved\
    +-- CHANGELOG.md

7.1 BASE

Defines the fundamental identity and role of the AI.

7.2 INTELLECTUAL STYLE

Defines how the AI reasons, explains, challenges assumptions and
connects ideas.

7.3 VOICE

Defines conversational characteristics for spoken interaction.

7.4 BEHAVIOURS

Defines when the AI listens, assists, asks, suggests, waits or speaks.

7.5 BOUNDARIES

Defines safety, privacy, editorial and operational limits.

7.6 RELATIONSHIPS

A relationship file may be created for a recurring host or participant
when there is a legitimate production reason.

The filename may use the Buzzjuice username where appropriate.

Relationship files should describe interaction characteristics, not
become hidden psychological dossiers.

7.7 PERSONA VERSIONING

Every approved change gets a version.

Example:

    v0.1
    v0.2
    v0.3

A proposal is not a live persona change.

======================================================================
8. PERSONA EVOLUTION
======================================================================

The AI Desk learns from episodes indirectly.

The lifecycle is:

    EPISODE
       |
       v
    TRANSCRIPT
       |
       v
    POST-EPISODE ANALYSIS
       |
       v
    PERSONA OBSERVATION
       |
       v
    PERSONA PROPOSAL
       |
       v
    PRODUCER REVIEW
       |
       +---- REJECT
       |
       +---- APPROVE
                |
                v
          PERSONA VERSION
                |
                v
             CHANGELOG

The AI must never infer:

    "I observed it, therefore it is now part of my personality."

Instead:

    "I observed it; I propose it; the producer approves it."

This is the principal control against personality drift.

11. CONTEXT STATUS

It should identify:

- episode identity
- context version
- lifecycle status
- completeness
- validation status
- consent state

- last update

Example state values:

    recorded
    post_production
    ready_for_retrieval

    continuity: complete

    consent: verified

13. BIBLE REFERENCE
======================================================================

02_BIBLE_REFERENCE.md records the Bible reference used for the episode.

This supports the Eternal Dreamfall / Bible-study component of the
episode workflow.

The process is:

    CURRENT STUDY / REFERENCE
              |
              v
       SELECT PASSAGE
              |
              v
       IDENTIFY KEY VERSE
              |
              v
      RECORD REFERENCE
              |
              v
        EPISODE STORY

The file should contain:

- book
- chapter
- verses
- selected key verse
- translation
- why it is relevant
- source/reference information
- any editorial interpretation used

The AI Desk should not silently invent the passage.

The producer supplies or verifies the reference.

======================================================================
14. HEALTH & SAFETY REFERENCE
======================================================================

03_HEALTH_SAFETY_REFERENCE.md records the Health & Safety material used
by the episode.

The process is:

    Episode topic
        |
        v
    Health & Safety repository
        |
        v
    Identify relevant course/topic
        |
        v
    Retrieve source material
        |
        v
    Producer review
        |
        v
    Episode reference

The source may be a Git repository or another controlled repository.

The episode file should identify:

- source repository
- source path
- lesson/course
- relevant topic
- key facts
- selected references
- date/version
- producer notes

The episode owns the reference actually used.

The AI Desk stores the retrieval method and catalog reference, not a
second permanent copy of the entire Health & Safety curriculum.

======================================================================
15. CONTINUITY REFERENCE
======================================================================

04_CONTINUITY_REFERENCE.md records previous Chronicles material used to
connect the current episode to earlier episodes.

The process is:

    Current story question
           |
           v
    Search previous episodes
           |
           v
    Relevant episodes
           |
           v
    Relevant transcript/show-note chunks
           |
           v
    Producer selects continuity references
           |
           v
    Episode continuity record

Each selected reference should identify:

- episode ID
- source unit ID
- approximate timestamp when available
- reason for continuity
- intended use

This prevents the current episode from depending on an invisible
"AI memory."

        headline_expansion_prompt

    05_HEADLINES.json

    Location
       |
    Time window
       |
    Current news research
       |
    Candidate headlines
       |
    Producer review
       |
    Approved headlines
       |
    Episode Context

Headline records should include:

- stable headline ID
- title
- summary
- category
- source
- source URL where available
- publication time/date
- retrieval time/date
- suggested episode connection
- status
- expansion status

Statuses:

    candidate
    approved
    rejected
    expanded

This preserves historical truth about what was actually available at

20. CONSENT

32. DETAILED EPISODE WORKFLOW
======================================================================

32.1 CREATE THE EPISODE

Create:

    CC_Sxx_SEASON\
        Exx_TITLE\

Then create the standard folders.

32.2 INITIALIZE CONTEXT

Create:

    00_CONTEXT_STATUS.json

35. FTS5 RETRIEVAL
======================================================================

The initial full-text index should index meaningful units.

Do NOT make:

    one transcript = one record

Instead:

    transcript
       |
       +-- segment 001
       +-- segment 002
       +-- segment 003
       ...

Also index:

- show notes
- story notes where appropriate
- headlines
- research
- continuity references
- approved episode context

Each unit gets a stable identifier.

Example:

    S01E01:TRANSCRIPT:0042
    S01E01:HEADLINE:H003
    S01E01:RESEARCH:R007

The initial implementation may use lexical chunking. Later, timestamp-
aware speaker segmentation can replace it without changing the logical
ID model.

======================================================================
36. SEMANTIC RETRIEVAL
======================================================================

Semantic retrieval is intentionally deferred.

Only add it when real episodes demonstrate that FTS5 fails materially
on meaning-based queries.

Then use:

    SQLite FTS5
          +
    semantic retrieval
          |
          v
    hybrid ranking

Do not make FAISS or another vector layer a commissioning prerequisite.

Do not create a large embedding infrastructure before the archive has
enough real data to justify it.

45. AI MODES
======================================================================

LISTEN

The AI receives permitted input but does not speak.

This should be the initial commissioning mode.

ASSIST

The AI can provide producer-facing assistance but should not insert
itself into the live programme without an explicit production path.

CO-HOST

The AI can speak as a controlled participant.

AUTONOMOUS

The AI may operate within explicitly defined boundaries.

AUTONOMOUS is the final stage, not the starting point.

======================================================================
46. AI MUTE
======================================================================

AI MUTE is a production safety subsystem.

There should be:

    hardware / physical control
    software control
    UI indication

The AI must be muteable even if:

- the model hangs
- the UI fails
- retrieval fails
- network latency increases
- the provider becomes unavailable

The exact physical implementation remains governed by the existing
Studio audio architecture.

AI audio should remain independently controllable.

54. SCHEDULING DESIGN
======================================================================

The eventual scheduler should be a Windows Scheduled Task or equivalent
service invoking Node.js/PowerShell.

The schedule should trigger preparation, not uncontrolled publication.

Example:

    Tuesday evening:
        research + context preparation

    Friday morning:
        research + context preparation

The producer should receive a ready-to-review episode package.

The system should not silently publish an episode because a scheduled
task succeeded.

======================================================================
55. ARCHIVE SCANNING
======================================================================

The AI Desk must support scanning the entire Chronicles archive.

Example:

    C:\weblink\Classies_Chronicles\
             |
             +-- S00
             +-- S01
             +-- S02
             +-- ...

The scanner discovers:

- season
- episode
- context package
- metadata
- status
- permissions
- files
- hashes
- modification time

Then it updates the catalog.

This scanner is the foundation for supporting a local folder, Git
repository or synchronized cloud folder.

======================================================================
56. SOURCE HASHING
======================================================================

For rebuildability and change detection, context units should have a
content hash.

Example:

    SHA-256

When a file changes:

    old hash != new hash

The AI Desk knows that the source needs re-indexing.

This is preferable to blindly rebuilding the entire archive every time.

======================================================================
57. INDEX VERSIONING
======================================================================

The system should track:

    source version
    parser version
    index version

Example:

    source: 1.3
    parser: 0.4
    index: 12

If the parser changes, the index can be rebuilt.

======================================================================
58. REBUILDABILITY
======================================================================

The following should be rebuildable:

- catalog
- FTS5 index
- derived manifests
- retrieval caches

The following are authoritative:

- episode context
- consent manifests
- licensing manifests
- final episode assets
- approved persona files
- approved prompt versions

This distinction is essential for long-term maintainability.

======================================================================
59. ERROR HANDLING
======================================================================

The AI Desk should fail safely.

Examples:

MISSING EPISODE CONTEXT

    Do not index.

INVALID CONSENT

    Do not retrieve for restricted operation.

STALE INDEX

    Warn and rebuild.

MISSING SOURCE

    Return unavailable rather than inventing content.

AMBIGUOUS RETRIEVAL

    Ask producer or return uncertainty.

AI PROVIDER FAILURE

    AI MUTE / LISTEN state remains safe.

NETWORK FAILURE

    Local archive remains usable where possible.

    Git history

67. WHAT WAS MODIFIED
======================================================================

The GitHub/Copilot proposal is not adopted literally.

Modifications:

1. Episode Context was expanded to include explicit:
   Bible, Health & Safety, Continuity, Production Requirements,
   Transcript and Episode Changelog stages.

2. The episode contract was reordered to reflect the actual production
   lifecycle.

3. The catalog is explicitly rebuildable and is not the source of truth.

4. Permission state is separated from mere index presence.

5. Storage is abstracted through logical episode IDs.

6. NotebookLM is explicitly treated as an episode-stage narrative tool,
   not as the AI Desk.

7. The Buzzjuice MU plugin is treated as a future controlled API
   boundary, not an initial commissioning dependency.

8. The AI Desk is prevented from becoming a participant/CRM database.

9. Automation is preparation-first and approval-gated.

10. Semantic retrieval remains deferred.

11. AI audio remains separate and muteable.

12. Python is not prohibited, but is no longer the default automation
    layer.
