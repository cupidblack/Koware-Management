# 1. Executive Architecture

The Pavilion is the Studio's **Guest Communications Desk**.

All guest-facing communication should pass through one reusable audio architecture.

The calling service is therefore treated as a **replaceable communications gateway**, not as the Studio's audio architecture.

Supported gateways include:

* WhatsApp
* Google Meet
* Zoom
* Riverside
* Microsoft Teams
* other compatible calling applications

The permanent Studio audio architecture is:

```text
                    STUDIO PAVILION

                         HOST
                          │
                       BLUE YETI
                          │
                          ▼
                  ┌───────────────┐
                  │  VOICEMEETER  │
                  │     POTATO    │
                  └───────┬───────┘
                          │
              ┌───────────┼───────────┐

             A1          B1          B2
              │           │           │

              │                        │
```

The permanent bus contract is:


This is the central Studio architecture.

Voicemeeter Potato officially provides five physical buses/outputs and three virtual I/O paths, with A1 determining the DSP engine sample rate. ([VB-Audio][2])

# 2. The Communication Requirement

The system must provide:

```text
HOST ↔ GUEST
HOST ↔ AI
GUEST ↔ AI
```

while preventing:

```text
HOST → HOST
GUEST → GUEST
AI → AI
```

There are two different classes of feedback that must be controlled:

### Digital feedback

Caused by incorrect Voicemeeter routing.

### Acoustic feedback

Caused by speakers physically feeding the microphone.

Both must be addressed.

# 3. Canonical Participant Matrix

| Participant     | Host | Guest |  AI |
| --------------- | ---: | ----: | --: |
| **Host hears**  |  YES |   YES | YES |
| **Guest hears** |  YES |    NO | YES |
| **AI hears**    |  YES |   YES |  NO |

Therefore:

```text
HOST
 ├──→ GUEST
 └──→ AI

GUEST
 ├──→ HOST
 └──→ AI

AI
 ├──→ HOST
 └──→ GUEST
```

and:

```text
HOST → HOST = BLOCKED
GUEST → GUEST = BLOCKED
AI → AI = BLOCKED
```

# 4. Why Mix-Minus Is the Core

Each destination receives the conversation **minus itself**.

For the guest:

```text
Guest receives:

HOST + AI

NOT:

GUEST
```

For the AI:

```text
AI receives:

HOST + GUEST

NOT:

AI
```

For the host:

```text
Host receives:

GUEST + AI

and may optionally monitor HOST
```

The crucial distinction is that the Studio buses are not merely "audio outputs."

They are **semantic communication buses**.

Initial priority:

```text

```

```text
MME
```


ASIO should be reserved for applications that specifically require it, particularly DAW/production workflows.

The objective is:

```text
STABILITY FIRST
LATENCY SECOND
```

* crackling
* dropouts
* buffer underruns
* device resets
* clock instability

# 35. Host Processing

The Blue Yeti may eventually use:

```text
Noise Reduction
 ↓
Gate
 ↓
EQ
 ↓
Compression
 ↓
Routing
```

Start conservatively.

The objective is:

* intelligibility
* consistent level
* reduced room noise
* stable AI recognition

Do not use aggressive gating that cuts off words.

Do not heavily compress the host before the basic routing is proven stable.

Potato provides built-in gate, compressor, denoiser and EQ functionality, so additional processing software should not be introduced prematurely. ([VB-Audio][2])

# 43. Failure-Diagnosis Matrix

| Symptom                         | Likely Cause                             | Corrective Action                       |
| ------------------------------- | ---------------------------------------- | --------------------------------------- |
| Guest hears themselves          | Guest Return → B1                        | Set B1 OFF                              |
| AI hears itself                 | AI Return → B2                           | Set B2 OFF                              |
| Host hears echo                 | Acoustic or duplicate monitor path       | Headphones; remove duplicate monitoring |
| Guest hears delayed host        | Duplicate application/Windows monitoring | Check app and Windows routing           |
| AI repeatedly responds          | AI return entering B2                    | B2 OFF on AI return                     |
| AI misses guest                 | Guest return not reaching B2             | B2 ON on Voicemeeter Input              |
| Guest cannot hear host          | Host not reaching B1                     | B1 ON on Blue Yeti                      |
| Guest cannot hear AI            | AI return not reaching B1                | B1 ON on AI return                      |
| Host cannot hear guest          | Guest return not reaching A1             | A1 ON on Voicemeeter Input              |
| Crackling/dropouts              | Buffer/driver/clock issue                | Increase buffer; test WDM/MME/KS        |
| Unexpected system audio in call | Global Windows routing                   | Use explicit per-app routing            |

### The key upgrade from the earlier version

The architecture itself **doesn't need another major routing change**. The significant refinement is the boundary between **audio transport, AI participation, and the AI Desk**.

Voicemeeter Potato is capable of the required virtual I/O and bus structure, so keeping VB-CABLE out of the commissioning stage is the right decision. ([VB-Audio][2]) The GitHub module also supports keeping the caller return off B1 and feeding it to A1+B2. ([GitHub][3])

The one thing I would **not** carry forward from the previous recommendations is the claim that direct ChatGPT Voice gives a guaranteed production-grade three-person conversation. OpenAI currently says Live can listen and speak simultaneously, but also explicitly says it is primarily designed for one-on-one conversation and isn't optimized for several people speaking to it at once. ([OpenAI Help Center][1])

So the Studio architecture should be:

**Voicemeeter = permanent audio infrastructure**
**Calling app = replaceable guest gateway**
**AI Bridge = future production AI participant**
**AI Desk = persistent Studio knowledge/context layer**

That separation is what will let us scale the Pavilion into the wider Studio system without having to rebuild the audio architecture later.
